# Contributing to AI Structural Philosophy Academic Framework

Thank you for your interest in contributing to **AI Structural Philosophy Academic Framework**.

This repository is not only a documentation project, but a proposal for a unified academic framework connecting:

- internal structure
- behavioral generation
- value configuration
- structural safety
- societal implementation

Because of that, contributions should aim not only for clarity and usefulness, but also for **conceptual precision**, **structural consistency**, and **epistemic discipline**.

---

## Guiding Principle

This project is built on a simple principle:

> Do not treat AI only as output.  
> Treat it as structure.

Contributions should help strengthen that principle through better definitions, cleaner organization, clearer methods, stronger falsifiability, and more rigorous connections between concepts.

---

## What kind of contributions are welcome?

We welcome contributions such as:

- terminology improvements
- typo fixes and wording clarifications
- structural improvements to the framework
- clearer definitions
- stronger research question design
- better methodological organization
- improved documentation
- new examples that clarify concepts
- consistency fixes across files
- roadmap refinements
- benchmark or evaluation ideas
- audit and governance extensions
- YAML / JSON / schema alignment improvements, if the repository later includes them

---

## What kind of contributions are **not** a good fit?

The following are generally **out of scope** unless explicitly discussed first:

- purely promotional edits
- vague philosophical expansion without structural grounding
- claims presented as facts without sufficient support
- terminology inflation that reduces clarity
- changes that break core conceptual consistency
- unrelated AI news additions
- ideology-first edits that weaken falsifiability
- anthropomorphic claims presented as established truth
- replacing precise concepts with fashionable but less rigorous language

In short:

> Add structure, not noise.

---

## Before you contribute

Please read the following first:

- `README.md`
- `CHANGELOG.md`
- `CITATION.cff`
- the current framework specification files

Before proposing a major change, make sure you understand the repository’s core chain:

**internal structure → behavioral generation → value configuration → safety profile → societal implementation**

If your proposed contribution does not strengthen at least one part of this chain, it may not fit the project.

---

## Types of contributions

### 1. Editorial contributions
Examples:

- grammar fixes
- wording improvements
- formatting cleanup
- heading consistency
- glossary alignment

These are usually straightforward and welcome.

### 2. Conceptual contributions
Examples:

- refining definitions
- adding or restructuring chapters
- improving core concepts
- clarifying axioms
- strengthening methodological distinctions

These require careful reasoning and should preserve the internal integrity of the framework.

### 3. Methodological contributions
Examples:

- new validation criteria
- falsifiability refinements
- experiment template suggestions
- comparative analysis methods
- audit protocol proposals

These are highly valuable when clearly scoped and well justified.

### 4. Structural / specification contributions
Examples:

- YAML cleanup
- schema compatibility improvements
- metadata consistency
- machine-readable spec organization
- versioning structure improvements

These contributions should preserve readability and conceptual meaning.

---

## How to contribute

### For small fixes
You may open a pull request directly for:

- typos
- broken formatting
- small wording corrections
- minor consistency fixes

### For larger changes
Please open an issue first if you want to propose:

- a new major concept
- a new chapter
- a restructuring of the framework
- a new methodology section
- a major change in terminology
- a substantial change in scope

This helps keep conceptual changes coherent before implementation begins.

---

## Pull request guidelines

Please keep pull requests:

- focused
- readable
- limited in scope
- well explained

A good pull request should answer:

1. What is being changed?
2. Why is this change needed?
3. Which part of the framework does it improve?
4. Does it affect terminology, structure, methodology, or scope?
5. Does it preserve consistency with the rest of the framework?

If applicable, include before/after wording or a short rationale.

---

## Style guidelines

### Writing style
Prefer writing that is:

- precise
- calm
- readable
- conceptually disciplined
- non-hyped
- non-redundant

Avoid writing that is:

- overly promotional
- vague
- inflated
- slogan-heavy
- emotionally manipulative
- needlessly anthropomorphic

### Terminology
Use terms consistently.

Examples of important distinctions:

- **internal structure** is not the same as output
- **emotion-related representation** is not the same as human subjective emotion
- **persona** is not the same as fixed selfhood
- **structural safety** is not the same as output filtering
- **value direction** is not the same as a simple rule list

If you introduce a new term, define it clearly and explain why an existing term is insufficient.

### Tone
This repository should remain serious, rigorous, and constructive.

The tone should feel closer to:

- academic framing
- conceptual engineering
- research design
- protocol drafting

and less like:

- personal branding copy
- trend-chasing commentary
- speculative mystification

---

## Conceptual integrity rules

Contributors should preserve the following project commitments:

### 1. Structure comes first
The framework is built around structure, not superficial behavior alone.

### 2. Explanation must remain causal
Claims should try to connect internal structure and behavior through causal reasoning, not only analogy.

### 3. Normative claims should be explicit
If a proposal is descriptive, say so.  
If it is normative, say so.

Do not blur these without explanation.

### 4. Falsifiability matters
This repository is not meant to be immune to revision.  
Changes should strengthen the framework’s ability to be tested, challenged, and refined.

### 5. Clarity beats novelty
A clear existing term is usually better than a flashy new one.

---

## Evidence and support

For major conceptual claims, please provide one or more of the following when possible:

- a clear reasoning chain
- a comparison to an existing section in the framework
- a concrete use case
- an experimental implication
- a validation path
- a falsifiability condition
- reference to relevant research literature

This repository does not require that every idea be fully proven before discussion, but strong contributions should move ideas toward greater testability and clarity.

---

## File-level expectations

### `README.md`
Should remain readable to newcomers and reflect the project at a high level.

### `CHANGELOG.md`
Should record meaningful structural and conceptual changes.

### `CITATION.cff`
Should remain accurate and up to date.

### Spec files
Should preserve:

- terminology consistency
- version clarity
- machine readability where applicable
- human readability at the conceptual level

---

## Versioning philosophy

This repository uses versioning for **conceptual and structural changes**, not just technical edits.

Examples:

- `0.1.x` may include clarification, cleanup, and small refinements
- `0.2.0` may add methodological depth or evaluation structure
- `0.3.0` may extend audit or governance layers
- `1.0.0` should represent a stabilized reference framework

A version bump should reflect a meaningful change in the framework itself.

---

## Commit message suggestions

Examples:

- `docs: clarify definition of structural safety`
- `docs: improve chapter structure in README`
- `spec: refine value direction terminology`
- `spec: add falsifiability note for persona selection`
- `meta: update citation metadata`
- `chore: align terminology across files`

Keep commit messages short, clear, and specific.

---

## Review criteria

Pull requests may be reviewed according to the following questions:

- Is the contribution conceptually clear?
- Does it improve the framework?
- Is the terminology consistent?
- Does it preserve structural coherence?
- Does it reduce ambiguity?
- Does it introduce unnecessary complexity?
- Is the proposed change testable, usable, or clarifying?

Not every contribution needs to be large.  
A small clarification that prevents conceptual drift can be more valuable than a large but noisy addition.

---

## Respect and collaboration

Please contribute in a way that is:

- respectful
- intellectually honest
- open to revision
- calm under disagreement

This project may involve philosophy, safety, ethics, and interpretability, which are all areas where strong disagreements can arise.  
That is fine.  
But disagreement should improve structure, not damage it.

Critique is welcome.  
Careless distortion is not.

---

## Attribution

By contributing, you agree that your contribution may become part of the evolving framework and repository history.

If citation-related metadata or authorship structure needs adjustment in the future, it should be discussed explicitly through issues or repository governance updates.

---

## Final note

The goal of this repository is not to make AI sound mysterious.

The goal is to make AI more understandable by giving structure to what is currently fragmented.

If your contribution helps make the framework clearer, stronger, more rigorous, or more useful, it is welcome.

Thank you for helping improve **AI Structural Philosophy Academic Framework**.
